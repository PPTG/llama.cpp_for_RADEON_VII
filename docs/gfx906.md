# llama.cpp for Radeon VII / Radeon Pro VII (gfx906)

HIP/ROCm changes for gfx906 (Radeon VII, Radeon Pro VII, Instinct MI50/MI60): token generation, two GPUs without peer
access, long context with a q8_0 KV cache, prompt processing and llama-server sampling. The [README](../README.md) has
the summary and the recommended settings; this page has the options, the measurements of every change and the tuning
scripts. Measured on 2x Radeon Pro VII, ROCm 7.1, mainly Gemma 4 26B A4B.

## Quick start

```bash
scripts/gfx906/run-all.sh models/<model>.gguf
```

Builds the variants (`nodpp` = upstream reductions, `dpp`, `nw1`, `nw4`), runs `test-backend-ops` against the CPU, runs `llama-bench` and profiles kernels with `rocprofv3`. Output: `results-gfx906/<date>/summary.txt` and a `.tar.gz` archive.

## Recommended settings (2 GPUs, long context, llama-server)

```bash
sudo rocm-smi --setperflevel high               # GPU clocks (tg +~10%)
sudo cpupower frequency-set -g performance      # CPU governor (kernel launches, sampling)

LLAMA_KV_SPLIT_HEADS=1 ./build-gfx906/bin/llama-server -m models/<model>.gguf \
    -ngl 99 -sm layer -fa on -ctk q8_0 -ctv q8_0 -c 120000 -np 1 -ub 1024 -b 2048
```

- `LLAMA_KV_SPLIT_HEADS=1`: half of the KV heads of the global layers (and their KV cache) on the other GPU. Prompt
  processing at long context +57% (d100000), about equal at d30000, -13% at d0; token generation equal. Uses a second
  stream per GPU (`LLAMA_KV_SPLIT_STREAM`, +0.5-0.8 GB VRAM per GPU at `-ub 1024`). Leave it off for short contexts.
- `-ub 1024`: prompt processing +14% over the default 512 (2048 is not faster). Lower it if the compute buffers do not
  fit next to a 120k context.
- `-sm layer`: faster than `-sm tensor` on two GPUs without peer access.
- q8_0 KV cache: the FA kernels read q8_0 directly in token generation; same quality as f16 within noise
  (`scripts/gfx906/quality.sh`).
- Everything else (fusions, MMVQ geometry, FA wave kernel, sampling / grammar fast paths, top-k MoE) is on by default;
  the environment variables below only turn things off or select tuning variants.

Gemma 4 26B A4B Q4_0, 2x Pro VII, these settings: tg ~110 t/s (llama-bench, d0) / ~128 t/s in llama-server,
prompt processing 1985 / 1168 / 567 t/s at d0 / d30000 / d100000.

## Gemma 4 26B A4B: which file

Gemma 4 has QAT (quantization aware trained) checkpoints made for Q4_0, so a Q4_0 of the QAT model is close to BF16,
and Q4_0 is also the type the kernels of this fork are tuned for. From the table of
[EZForever/gemma-4-26B-A4B-it-qat-uncensored-heretic-UDmerge-GGUF](https://huggingface.co/EZForever/gemma-4-26B-A4B-it-qat-uncensored-heretic-UDmerge-GGUF)
(their measurements, KLD vs QAT BF16, MMLU flips vs BF16):

| QAT file             | size    | KLD    | MMLU %flips | tg32 here (2 GPUs) |
|----------------------|--------:|-------:|------------:|-------------------:|
| Q4_0                 | 16.0 GB | 0.1158 | 3.53% |  |
| Q4_K_M (Unsloth)     | 16.8 GB | 0.1076 | 3.79% | ~90 t/s |
| UDmerge-Q4_K_XL      | 14.2 GB | 0.0448 | 3.66% | ~110 t/s |
| UDmerge-Q4_K_XXL     | 14.3 GB | 0.0291 | 0.98% |  |

- Q4_K_M keeps many tensors in q8_0: ~20% slower token generation here (bandwidth) without better accuracy on the QAT
  model.
- UDmerge-Q4_K_XXL differs from Q4_K_XL only by 12 `attn_output` tensors in q8_0 (+0.1 GB): lower KLD and far fewer
  MMLU flips for a negligible cost in token generation; q8_0 dense matmuls use the same tuned MMVQ geometry.
- The model card recommends Google's updated Gemma 4 chat template (`--jinja --chat-template-file <template>.jinja`).
- MTP (multi-token prediction, speculative decoding with the MTP head from the Unsloth `mtp` GGUF) is supported by
  llama.cpp: `--spec-type draft-mtp -md <mtp>.gguf --spec-draft-n-max 3`. Not measured on gfx906 yet; it runs the
  model on 2-4 tokens at once (small batch MMVQ, which is not tuned here like batch size 1).

## Installing ROCm 7.x on gfx906

ROCm 7.x no longer ships gfx906 kernels in rocBLAS (removed in ROCm 6.4.0). llama.cpp itself is compiled for gfx906 by
`scripts/gfx906/build.sh`, but it calls rocBLAS for some matrix multiplications (prompt processing, f16 / f32 matmuls),
and without the gfx906 Tensile files rocBLAS fails as soon as it is first used. The fix is the rocBLAS of ROCm 6.3.3,
the last release that built them. Setup of the test machine:

- Debian 13 (Proxmox VE 9, kernel `7.0.14-pve`), the in-kernel `amdgpu` driver (no DKMS).
- ROCm 7.2.1 from the AMD repositories for Ubuntu 24.04 (noble): AMD publishes no Debian 13 (trixie) repository, noble
  has the closest glibc and installs on Debian 13.
- rocBLAS of ROCm 6.3.3 unpacked (not installed) into `/root/rocblas-6.3.3/extracted/`, its 156 gfx906 files copied
  into the rocBLAS of the system ROCm 7.2.1.

1. AMD repositories (as in the AMD installation guide):

   ```bash
   sudo mkdir -p /etc/apt/keyrings
   wget -qO - https://repo.radeon.com/rocm/rocm.gpg.key | gpg --dearmor | sudo tee /etc/apt/keyrings/rocm.gpg > /dev/null
   sudo tee /etc/apt/sources.list.d/rocm.list << 'LIST'
   deb [arch=amd64 signed-by=/etc/apt/keyrings/rocm.gpg] https://repo.radeon.com/rocm/apt/7.2.1 noble main
   deb [arch=amd64,i386 signed-by=/etc/apt/keyrings/rocm.gpg] https://repo.radeon.com/graphics/7.2.1/ubuntu noble main
   LIST
   sudo apt update
   ```

2. ROCm without the kernel module (the in-kernel `amdgpu` of a recent kernel is enough):

   ```bash
   sudo apt install rocm-hip-sdk rocblas rocblas-dev hipblas hipblas-dev rocm-smi-lib rocminfo
   sudo usermod -aG render,video "$USER"      # log in again afterwards
   ```

3. rocBLAS of ROCm 6.3.3 (the Ubuntu 24.04 package), unpacked without installing:

   ```bash
   mkdir -p /root/rocblas-6.3.3/extracted && cd /root/rocblas-6.3.3
   wget https://repo.radeon.com/rocm/apt/6.3.3/pool/main/r/rocblas/rocblas_4.3.0.60303-74~24.04_amd64.deb
   dpkg-deb -x rocblas_4.3.0.60303-74~24.04_amd64.deb extracted/
   ls extracted/opt/rocm-6.3.3/lib/rocblas/library/ | grep -c gfx906      # 156 files
   ```

   and copy the gfx906 files into the system rocBLAS (what the test machine uses day to day):

   ```bash
   sudo cp extracted/opt/rocm-6.3.3/lib/rocblas/library/*gfx906* /opt/rocm/lib/rocblas/library/
   ```

   The copied files are not owned by a package: apt upgrades of rocBLAS leave them in place, a ROCm installed into a
   new `/opt/rocm-<version>` needs the copy again.

   Alternative without touching the system ROCm: leave the files in `extracted/` and set these variables for every run
   of llama-server, llama-bench and the tests (the test machine started this way; easy to forget, hence the copy):

   ```bash
   export ROCBLAS_TENSILE_LIBPATH=/root/rocblas-6.3.3/extracted/opt/rocm-6.3.3/lib/rocblas/library
   export LD_LIBRARY_PATH=/root/rocblas-6.3.3/extracted/opt/rocm-6.3.3/lib:${LD_LIBRARY_PATH:-}
   ```

4. Check:

   ```bash
   rocminfo | grep -E "Marketing Name|Name: +gfx906"
   scripts/gfx906/build.sh && ./build-gfx906/bin/test-backend-ops -o MUL_MAT -b ROCm0
   ```

hipBLASLt has no gfx906 kernels either; llama.cpp does not need it on gfx906.

## Results

2x Radeon Pro VII (PCIe, no bridge), ROCm 7.1, Gemma 4 26B A4B Q4_0 (UD Q4_K_XL, merged gate_up), `llama-bench -fa 1`,
upstream = 271158c6e, fork = fc331626b, all fork options at their defaults (`scripts/gfx906/final-bench.sh`):

| test           | 1 GPU upstream | 1 GPU fork | gain | 2 GPU layer upstream | 2 GPU layer fork | gain |
|----------------|---------------:|-----------:|-----:|---------------------:|-----------------:|-----:|
| tg128          |  96.6 | 115.9 | +20% |  82.8 | 107.9 | +30% |
| tg128 @ d4096  |  88.5 | 106.9 | +21% |  75.2 |  98.1 | +31% |
| tg128 @ d16384 |  86.2 | 101.8 | +18% |  75.9 |  92.7 | +22% |
| pp512          |  1398 |  1393 |   0% |  1394 |  1415 |  +2% |

Where the tg gain comes from (1 GPU / 2 GPU, from the A/B runs):

- DPP warp reductions: +3-7%
- staged copy between GPUs (2 GPU only): +14%
- MMVQ 1 warp x 8 rows on GCN: +4-8%
- Q8_1 activation cache (Q/K/V and gate/up quantized once): +1.5-3%

Round 2 (kernel count reduction, `rocm-smi --setperflevel high`, tg128, `scripts/gfx906/ab.sh`):

| Config                                   | 1 GPU | 2 GPU layer |
|------------------------------------------|------:|------------:|
| all on (default, 2514c9eb7)              | 124.7 | 115.2 |
| without Q/K/V multi MMVQ                 | 119.7 | 110.4 |
| without any fusion (`GGML_CUDA_DISABLE_FUSION=1`) | 93.2 | 86.6 |
| upstream MMVQ geometry                   | 105.6 |  99.0 |

New in round 2:

- Q/K/V (and shared gate/up) as one MMVQ launch: +4-5%
- rms_norm + scale + mul fused (MoE router input)
- expert scale looked up in the MoE weighted reduction (no repeat + get_rows)
- `rocm-smi --setperflevel high`: +5-9% on 2 GPUs (the idle GPU of the layer split does not clock down), no change on 1 GPU

Round 3 (0aa034c90, `rocm-smi --setperflevel high`, tg128, mean of 2 `scripts/gfx906/ab.sh` rounds):

| Config                                   | 1 GPU | 2 GPU layer |
|------------------------------------------|------:|------------:|
| all on (default)                         | 127.1 | 117.6 |
| without Q/K/V multi MMVQ                 | 118.2 | 110.7 |
| without glu + q8_1 fusion                | 127.9 | 115.8 |
| without multi output rms_norm            | 125.9 | 114.1 |
| without any fusion                       |  93.3 |  88.9 |
| upstream MMVQ geometry                   | 107.6 |  99.8 |

Q/K/V as one launch is the biggest single fusion (+6-8%). glu + q8_1 is neutral on 1 GPU (fewer launches, same work) and kept on since it is bit exact. All fork fusions give the same text as the unfused ops (`scripts/gfx906/check.sh`).

Round 4 (long context, q8_0 KV cache, 2 GPU layer split, `rocm-smi --setperflevel high`):

- glu + q8_1 fusion fixed: it never ran before (`ggml_can_fuse` requires equal shapes). tg128 f16 KV: 114.8 -> 122.9 t/s.
- q8_0 KV with head size 256 (SWA layers) on the FA tile kernel that reads q8_0 directly: 44 -> 34 us per call.
- Hadamard rotation of the quantized KV cache fused into the cache store and the attn_output quantization: +5% tg at depth 0.
- FA combine kernel with more blocks: -14 us per global layer.

| tg32 (`scripts/gfx906/long-ctx.sh`, before the glu fix) | d0 | d4096 | d8192 | d15000 |
|---------------------------------------------------------|---:|------:|------:|-------:|
| f16 KV                                                   | 112.6 | 104.4 | 101.3 | 98.1 |
| q8_0 KV, round 3                                         |  97.8 |  90.7 |  87.0 | 85.4 |
| q8_0 KV, round 4                                         | 101.0 |  95.6 |  95.7 | 95.9 |

After the glu fix and the tuned q8_0 FA variants (`GGML_CUDA_FA_Q8_CFG` defaults): q8_0 KV tg32 104.0 (d0), 99.0 (d15000),
96.2 (d32768); the SWA layers on the tile kernel are +10% at d32768 over the vector kernel (87.1).

Both GPUs at the same time (2 GPU layer split, q8_0 KV, tg32, mean of 3, `scripts/gfx906/split-heads.sh`):
`LLAMA_KV_SPLIT_HEADS=1` puts the second KV head of the 5 global layers (and its half of their KV cache) on the other
GPU, which computes that half of the attention while the device of the layer computes the other half.

| tg32              | d0    | d15000 | d32768 | d65536 |
|-------------------|------:|-------:|-------:|-------:|
| layer split       | 110.0 | ~97    | ~96.5  | 85.5   |
| + split KV heads  | 106.8 | 98.9   | 97.4   | 91.8   |

Prompt processing (pp4096 / pp1024, `-ub 1024`, t/s). The split attention stopped the overlap of the two GPUs on
consecutive ubatches (pipeline parallelism): the scheduler waited on the host for all work of a GPU before copying the
mask of the global layers (first used in a later graph split of the GPU), and the part of the other GPU queued behind
its next layers. Fixed by copying the user inputs at the first split of a backend, a second stream per GPU for the
split attention (`LLAMA_KV_SPLIT_STREAM`) and staged copies that do not reuse busy host slots:

| prompt processing              | d0   | d30000 | d100000 |
|--------------------------------|-----:|-------:|--------:|
| layer split                    | 2290 | 1214   | 361     |
| + split KV heads (before)      | 1404 | 975    | 581     |
| + split KV heads (now)         | 1975 | 1168   | 567     |

d100000 is pp1024, one ubatch (no overlap of ubatches possible); tg32 at d100000: 94 split heads, 94 layer split.

`-ub 1024` is faster than the default 512 for prompt processing (pp4096 split heads: 972 / 1228 / 1402 / 1365 t/s at
ub 256 / 512 / 1024 / 2048).

On the HP DL580 test machine the two GPUs are on different CPU sockets (NUMA nodes 0 and 3): no peer access, every copy
between the GPUs goes through host memory (`GGML_CUDA_PEER_COPY` stays off), and binding the process with `numactl` to
either node made no difference (the socket interconnect has the same speed between all nodes) (d0 / d15000: 108.5 / 99.4 default, 106.6 / 99.8 node 0, 109.0 / 99.9 node 3).

The gain grows with the context (the attention of a global layer is ~130 us at 15k, ~780 us at 128k), the fixed cost of
the extra device switches is ~3% at short context. `-sm tensor` (all matrices split, 2 AllReduce per layer) was slower:
93.0 / 80.3 t/s at d0 / d32768 (later build, tg32 d0 / d15000: layer + `LLAMA_KV_SPLIT_HEADS=1` 107.9 / 104.1,
tensor 90.5 / 77.9; `LLAMA_KV_SPLIT_HEADS` is off with `-sm tensor`). Token generation is bound by ~900 small kernels per token (~5 us minimum each), which a
split over two GPUs does not reduce, only big kernels (long context attention) gain from a second GPU.

FA of the global layers with the q8_0 KV cache (head 512, GQA 8, token generation), `GGML_CUDA_FA_Q8_WAVE` kernel vs
the tile kernel (`scripts/gfx906/fa-q8-wave.sh`, us per call; nh = KV heads, 1 = one GPU with `LLAMA_KV_SPLIT_HEADS=1`):

| KV rows | nh | tile | wave |
|--------:|---:|-----:|-----:|
|    4096 |  2 |   46 |   46 |
|   16384 |  1 |   79 |   71 |
|   16384 |  2 |  119 |  114 |
|   65536 |  1 |  222 |  181 |
|   65536 |  2 |  404 |  299 |
|  131072 |  2 |  775 |  540 |

tg32 (2 GPUs, `LLAMA_KV_SPLIT_HEADS=1`) d0 / d15000: 107.5 / 101.1 tile, 109.1 / 103.4 wave. ROCm 7.1: 128 VGPRs,
2 waves per SIMD, no spills (`scripts/gfx906/fa-q8-wave-regs.sh`).

`-sm tensor` (with `GGML_CUDA_P2P=1`) was 91 t/s before the MMVQ work: over PCIe without a bridge the per layer AllReduce costs more than it saves.

llama-server (2 GPU layer split, 512 tokens with sampling, `scripts/gfx906/server-bench.sh`):

| Server args             | tg t/s |
|-------------------------|-------:|
| default                 |  96.4  |
| `-bs`                   | 102.7  |
| `-np 1 -c 32768`        |  98.7  |
| `-bs -np 1 -c 32768`    | 103.1  |

Token generation launches ~900 small kernels per token, so the host CPU clock matters as much as the GPU clock: with
`rocm-smi --setperflevel high` and `cpupower frequency-set -g performance` llama-server reached 128 t/s on the test
machine (2 GPUs, `LLAMA_KV_SPLIT_HEADS=1`).

ROCm runtime settings made no difference beyond the noise (tg32 d0 / d15000, `scripts/gfx906/tune-rocm-env.sh`):
default 110.3 / 98.3 (±11 at d15000), `HSA_ENABLE_SDMA=0` 106.2 / 103.6, `HIP_FORCE_DEV_KERNARG=1` 110.0 / 105.9,
`HSA_ENABLE_INTERRUPT=0` 110.1 / 103.8, `GPU_MAX_HW_QUEUES=1` 106.1 / 101.9, all three 109.0 / 104.6.

Recommended: `rocm-smi --setperflevel high`, `cpupower frequency-set -g performance` and `llama-server -m model.gguf -ngl 99 -fa on -bs`. Backend sampling runs the whole default sampler chain on the GPU. The server falls back to CPU sampling for requests with a grammar (JSON schema, tool calls), with logprobs, or with DRY/XTC/typical/top-n-sigma enabled.

Compare the multi GPU variants and check their output: `scripts/gfx906/multi-gpu.sh`.

## Build

```bash
scripts/gfx906/build.sh                      # -> build-gfx906/
```

Build options specific to this fork:

| CMake option                    | Default | Description |
|---------------------------------|---------|-------------|
| `GGML_HIP_NO_DPP_REDUCE`        | `OFF`   | Disable the DPP based warp reductions (fall back to upstream `__shfl_xor`). |
| `GGML_HIP_MMVQ_GCN_NWARPS`      | `2`     | Warps per block of the upstream MMVQ heuristics on GCN/CDNA (1, 2, 4, 8). Only used with `GGML_HIP_MMVQ_VARIANT=0`; the default is the tuned variant (see below). |

Runtime options:

| Env variable               | Description |
|----------------------------|-------------|
| `GGML_CUDA_STAGED_COPY=0`   | Default on for HIP: copy tensors between GPUs through pinned host memory with async D2H + H2D (no host stall), instead of the HIP runtime peer copy. `0` goes back to the peer copy. |
| `GGML_CUDA_PEER_COPY=1`     | Experimental: copies up to 1 MB between the GPUs (layer split boundaries, `LLAMA_KV_SPLIT_HEADS`) by a kernel that writes into the memory of the other GPU (peer access over PCIe) instead of D2H + H2D through pinned host memory. Test with `scripts/gfx906/peer-copy.sh`. |
| `GGML_CUDA_AR_P2P=1`        | `-sm tensor` with 2 GPUs: the AllReduce kernel writes directly into the VRAM of the peer and polls local VRAM, instead of staging through host memory. Needs P2P over PCIe. |
| `GGML_CUDA_MMVQ_Q8_CACHE=0` | Default on for HIP: quantize the activations (src1) once for consecutive MMVQ ops that use the same src1 (Q/K/V, gate/up). `0` quantizes for every op. |
| `GGML_HIP_MMVQ_VARIANT=<0..11>` | MMVQ geometry for batch size 1, warps per block x rows per block: 1: 1x1, 2: 1x2, 3: 1x4, 4: 2x1, 5: 2x2, 6: 4x1, 7: 4x2, 8: 1x8, 9: 1x16, 10: 2x4, 11: 2x8. Unset: 8 on GCN (+10% tg on Pro VII), 10 for q8_0 experts (MUL_MAT_ID; Gemma 4 gate_up 1408x2816: 55 -> 51 us). 0: upstream heuristics. Sweep with `scripts/gfx906/tune-mmvq.sh`, per shape and weight type with `TYPE=q8_0 scripts/gfx906/tune-mmvq-shapes.sh` (8 is the fastest for all dense shapes of q4_0, q8_0, q4_K, q5_1). |
| `GGML_HIP_MMQ_Q4_0_VARIANT=<0..6>` (compile time) | q4_0 MMQ tile configuration on GCN for prompt processing (`mmq-config-gcn.cuh`): 0 default (I 64, J up to 64, 256 threads), 1 as Q5_0, 2 as Q8_0 (512 threads, I 128, J up to 128), 3 default + J up to 128, 4 I 128 with 256 threads, 5 default with occupancy 1, 6 as Q8_0 with occupancy 1. Set through the untracked `ggml/src/ggml-cuda/mmq-config-gcn-local.h`; sweep with `scripts/gfx906/tune-mmq-shapes.sh`. Result on Pro VII: 0 is the fastest or equal for every Gemma 4 shape (larger tiles 20-80% slower, most on MUL_MAT_ID; occupancy 1 no change). Default q4_0 MMQ reaches ~16 TOPS dense (4096x2816x1024: 1.44 ms) and 11-12 TOPS for the experts (of ~54 TOPS int8 dot4 peak). |
| `GGML_HIP_MMQ_Q8_0_VARIANT=<0..3>` (compile time) | q8_0 MMQ tile configuration on GCN for prompt processing: 0 default (512 threads, I 128, J up to 128), 1 as the q4_0 default (256 threads, I 64, J up to 64), 2 256 threads with I 128, 3 default with J up to 64. Same mechanism as the q4_0 variants; sweep with `TYPE=q8_0 scripts/gfx906/tune-mmq-shapes.sh <model with q8_0 tensors>`. |
| `GGML_CUDA_FUSE_GATE_UP=1`  | Fuse merged gate_up weights (e.g. `ffn_gate_up_exps`) + glu into one MMVQ kernel, and add the alloc deps that let mm + glu fusions happen. Default off for HIP: ~5% slower on gfx906 (2x registers). |
| `GGML_CUDA_NORM_BLOCK_THRESHOLD=<n>` | RMS norm rows shorter than n use 256 threads per block, longer rows 1024 (default n = 1024). |
| `GGML_CUDA_FUSE_QKV=0`      | Default on for HIP: consecutive mul_mat with the same src1 (Q, K, V) run as one MMVQ launch; graph_optimize moves them next to each other. |
| `GGML_CUDA_FUSE_GLU_Q8=0`   | Default on for HIP: a glu that only feeds a MMVQ mul_mat (ffn_down) is computed and quantized to q8_1 in one kernel. |
| `GGML_CUDA_FUSE_NORM_MULTI=0` | Default on for HIP: up to 3 rms_norm -> [scale ->] mul chains on the same input run as one kernel; graph_optimize moves them next to each other. |
| `GGML_CUDA_FA_TILE_Q8=0`    | Default on: the FA tile kernel (head size 256/512, token generation) reads a q8_0 K/V cache directly instead of converting the whole cache to f16 on every call. |
| `GGML_CUDA_FUSE_FWHT=0`    | Default on for HIP: with a quantized KV cache llama.cpp rotates Q/K/V and the attention output with a Hadamard transform (fwht). The rotation of K and V runs in the kernel that stores them into a q8_0 cache, the rotation of Q in the fused rms_norm + mul + rope kernel, the rotation of the attention output in the q8_1 quantization for `attn_output`. `LLAMA_ATTN_ROT_DISABLE=1` turns the rotation off (llama.cpp option, slightly lower KV quality). |
| `GGML_CUDA_FA_Q8_VEC=1`    | q8_0 KV cache, head size 256, token generation: use the FA vector kernel. The default on HIP is the tile kernel, which reads q8_0 directly (Gemma 4 SWA layers 48 -> 39 us or less, GQA 16 2-3x faster). Compare with `scripts/gfx906/fa-tune.sh`. |
| `GGML_CUDA_FA_COMBINE_SPLIT=0` | Default on: the kernel that combines the partial FA results of long KV caches runs 64 values per block (more blocks for few heads) instead of one block per head. Same result. |
| `GGML_CUDA_FA_Q8_CFG=0/2/3` | Tuning variants (2: 128 K columns per step, 3: occupancy 3) of the FA tile kernel that reads q8_0, for head size 512 with GQA 8 and head size 256 with GQA 2. Default on HIP: 3 for head 512 (occupancy 3; 128k: 985 -> 846 us, with the prefetch 782 us), 0 for head 256 with the prefetch (34 -> 24 us; 2 without it). 0 = upstream config. Compare with `scripts/gfx906/fa-q8-cfg.sh`. |
| `GGML_CUDA_FA_PP_CFG=<n>`, `GGML_CUDA_FA_PP_CFG_256=<n>` | Prompt processing variants of the f16 FA tile kernel (the q8_0 cache is converted) for head size 512 with GQA 8 and head size 256 with GQA 2 (Gemma 4). Head 512 (default 32 Q columns, 512 threads, 128 KV rows x 64 K columns per step): 11: 256 threads occupancy 2, 64 KV rows; 14: 256 threads, 128 KV rows; 15 / 16 / 17: 16 Q columns (256 threads occ. 2 / 512 threads / 256 threads 64 KV rows). Head 256 (default 32 columns, 256 threads, 32 x 128): 11 / 12: 64 KV rows (256 / 512 threads); 13: 32 x 64; 15 / 16: 64 Q columns. 64 columns do not fit into 64 KB LDS at head 512. Default 0 = upstream config. Compare with `scripts/gfx906/tune-fa-pp.sh`. Result on Pro VII (q8_0 KV, ubatch 1024, 1 KV head): head 512 default fastest (kv 32768: 61.9 ms = ~8.9 TFLOPS of ~27 fp16; 11 / 14 / 16 / 17: +7..41%, 15: +130%); head 256 kv 2048: 5.19 ms upstream, 11: 6.64, 12: 4.49, 13: 4.35, 15: 5.85, 16: 4.28; 13 is the default for head 256 on HIP (`GGML_CUDA_FA_PP_CFG_256=0` for upstream), ~1% of prompt processing (the SWA layers are ~9%). |

## Changes

### DPP warp reductions (GCN5)

On AMD, `__shfl_xor` is compiled to `ds_bpermute_b32`, which goes through the LDS unit and waits on `lgkmcnt` at every step.
A full wave64 reduction was 6 such round trips. On GCN5 it is now:

- 4 steps with DPP (`quad_perm`, `row_half_mirror`, `row_mirror`), fused by the compiler into `v_add_f32_dpp`,
- 1 `ds_swizzle_b32` (swap 16),
- 2 `v_readlane_b32` for the last step (wave64 only).

This affects every kernel that uses `warp_reduce_sum`/`warp_reduce_max`: MMVQ (the final reduction of each row),
Q8_1 quantization of activations, RMS norm, softmax, top-k MoE routing, and flash attention.
At batch size 1 with MoE models the matrices are small (e.g. K = 2816), so the MMVQ K loop runs only a couple of
iterations and the final reduction is a noticeable fraction of the kernel time.
